3. WINDOWS IDENTITY OPTIONS AND CONCRETE API HAZARDS

W-A. Session-only, explicitly ephemeral identity (preferred proof candidate).
Potential APIs: CngKey.Create(CngAlgorithm.ECDsaP256, keyName:null,
CngKeyCreationParameters) with a reviewed software provider and creation/export
policy; ECDsaCng wrapping an owned ephemeral key; alternatively ECDsa.Create(
ECCurve.NamedCurves.nistP256), whose Windows implementation/lifetime must be
confirmed for the exact runtime. No API invocation is authorized now.
An unnamed CNG key is documented as ephemeral; this is an assumption to verify,
not evidence that every wrapper/certificate operation preserves that lifetime.
Do not introduce a name, PersistKeySet, machine scope, overwrite, provider fallback
or alternate KSP on failure. A nonexportability request/readback is not causal
policy proof; B1 export success proved neither nonexportability nor persistence.

After owner selects exact flags: creating the key is the FIRST native mutation.
CertificateRequest construction and extension encoding prepare certificate data;
CreateSelfSigned performs signing and creates an X509Certificate2 association.
CopyWithPrivateKey, GetECDsaPrivateKey and provider wrapping may acquire/duplicate
native handles. Public X509CertificateLoader.LoadCertificate loads DER into native
certificate structures; it is not an OS store installation and is still a native
operation requiring approval. Handle aliasing/lifetime must be traced, not guessed.
Use a test-only self-signed leaf, P-256, serverAuth EKU OID1.3.6.1.5.5.7.3.1,
digitalSignature usage, non-CA basic constraints, and exact IP SAN type7 bytes.
Validity/endpoint are owner-specified, never invented timestamps for snapshots.
No PKCS12/private export, DPAPI, certificate-store Add or socket is needed for W1.
Private-key ownership must survive TLS use and end only after all users drain.

W-B. DPAPI CurrentUser-protected exportable envelope (NOT selected).
Potential APIs: certificate.Export(X509ContentType.Pkcs12,...) or the supported
PKCS12 export API, ProtectedData.Protect/Unprotect with DataProtectionScope.CurrentUser,
and X509CertificateLoader.LoadPkcs12 with explicit X509KeyStorageFlags.EphemeralKeySet.
These involve private export, plaintext in process, profile-bound DPAPI and native
import. DPAPI may itself involve profile master-key state; do not describe it as
only a file write. A normal loaded user profile and exact Windows/runtime support
must be prerequisites. Account reset, missing profile, restore/roaming and user
context changes can make unprotect fail; disable rather than fall back to machine
scope or plaintext. ACL/nonreparse checks, atomic durable replacement and bounded
buffers require a separately reviewed storage plan. Password protection on PFX is
not the storage security boundary. Managed/OS copies cannot be globally zeroized.
Critical conflict: encrypted exportable key material does NOT satisfy the existing
NonExportable prerequisite. No bool, storage enum or quiet rule relaxation resolves
that. Owner must explicitly approve a revised policy before production consideration.

W-C. Owner-selected pre-existing identity (alternative, NOT selected).
X509Store(StoreName.My, StoreLocation.CurrentUser), Open(ReadOnly), explicit exact
certificate selection and GetECDsaPrivateKey may touch OS store/KSP/profile state,
access checks and potentially provider UI. Pre-existence alone does not establish
ownership/protection or permission to use it. No broad scan/adoption, ACL repair,
key deletion or mutation is allowed. A separately owned test identity would require
fresh scope; older A2 resources are categorically excluded.

W-D. Newly named persisted identity (excluded).
CngKey.Create with non-null name / NCryptCreatePersistedKey plus finalize can create
state before independent durable binding. Dispose/NCryptFreeObject is not deletion.
This is the Option2 orphan window. No D3 design depends on its harness or attempts
to solve it by name-only recovery, retry, best-effort delete or provisional records.

Flag/lifetime checklist for later proof:
- EphemeralKeySet is a private-key import storage flag, not a proof about an
  unrelated key created earlier; public DER LoadCertificate has no imported key.
- UserKeySet/MachineKeySet choose scope, not ephemerality. DefaultKeySet or legacy
  PFX constructor defaults must not silently choose profile/persistent storage.
- PersistKeySet is excluded. Exportable changes policy. UserProtected can request
  UI; no UI-free guarantee follows from flags0, Silent or successful earlier tests.
- X509Certificate2.Dispose and key-wrapper Dispose release owned references. They
  do not prove deletion of separately persisted containers. NCryptDeleteKey success
  consumes its handle; no such deletion is part of these proposed ephemeral proofs.
- Define who owns each key, certificate and wrapper and the disposal order.
  Avoid double disposal of aliases; release leaf/TLS users before underlying key.
- Normal process exit may release ephemeral handles. Abrupt death bypasses finally;
  persisted side effects survive. Unexpected named state/UI makes the run STOP/
  INCONCLUSIVE, never permission to enumerate or clean a store.
- Do not infer absence of side effects from a missing UI, one clean process exit
  or a filesystem snapshot. Any broader observation needs its own permission.

Current build: minSdk26, compileSdk35, targetSdk35, JVM17. Proposed proof coverage

Concrete JSSE candidates: CertificateFactory.getInstance("X.509") for public DER;
an in-memory java.security.KeyStore holding only this PC's exact anchor;
TrustManagerFactory.getInstance(defaultAlgorithm).init(thatStore); SSLContext(
"TLS"); SSLSocket/SSLSocketFactory; SSLParameters.setEndpointIdentificationAlgorithm(
"HTTPS"); SSLSocket.startHandshake; SSLSession peer certificates. These load/
allocate native/platform resources and are NOT run in this stage. This per-client
anchor store is NOT system/user trust-store installation or AndroidKeyStore.

Path validation must delegate to the platform X509TrustManager and preserve every
failure. Endpoint verification must remain enabled. Exact IP SAN verification uses
X509Certificate.getSubjectAlternativeNames type7 value, canonical literal parsing
with no DNS resolution, equivalent IP bytes and exact approved endpoint semantics;
SPKI is SHA256 of PublicKey.getEncoded, constant-time expected-byte comparison
(e.g. MessageDigest.isEqual), independently derived from actual peer certificate.
checkValidity plus serverAuth EKU, basic constraints/usage, path/anchor constraints
and current trust-generation/revocation checks all remain required. A pinned cert
does not waive validity/EKU/path checks, including when the leaf itself is an anchor.

Self-signed leaf as narrow anchor is an UNPROVEN compatibility hypothesis across
Android/JSSE versions. If platform validation rejects it, STOP and compare a dedicated
test CA+leaf alternative under new approval; never use an accept-all TrustManager.
Anchor-chain certificate revocation policy for private/offline PKI is undecided;
phone credential revocation and local PC trust-generation invalidation are distinct
and required, not a substitute for a stated certificate compromise/rotation policy.

Critical pre-credential gate: a standalone SSLSocket proof can perform full TLS,
path/hostname/SAN/pin checks and generation validation BEFORE any application write.
It must use no credentials at all in early experiments. HttpsURLConnection is a
later integration candidate, not a proven way to connect, inspect a pin and then
modify an already-connected Authorization header. That sequence may already have
committed headers or disallow changes; it is NOT an acceptable security design.
Before future HTTP use, prove either a strict platform-delegating
X509ExtendedTrustManager boundary that checks all required socket/engine overloads
before handshake success, or a vetted HTTP client's built-in pre-request pin gate
with normal trust/hostname checks. Neither is implemented/approved. A wrapper
must never swallow errors, silently use a default trust-all path or expose trusted
evidence via a boolean. Any third-party library requires separate dependency review.
No permissive HostnameVerifier, CN/DNS alias/wildcard fallback, HTTP fallback,
redirect with credentials, silent TOFU, silent pin reset or platform store mutation.

Dedicated client/session per PC, exact endpoint and trust generation; connection
pool/resumption cannot survive revoke/rotation/endpoint change unchecked. Disable
automatic redirects and retries; explicitly scope proxy behavior. On cancel,
close the owned socket or disconnect connection, join work and report uncertainty;
interrupt alone is not proof of closed I/O. No background reconnect/polling yet.
Offline means offline/stale, never demo-as-live. D3.2's wire/domain provenance gap
remains: readAt is receipt, observedAt is observation, lastKnown stays historical;
duplicate revisions never refresh measurement age and unknowns do not become0%.

Keystore design only: AndroidKeyStore KeyGenerator / KeyGenParameterSpec for a
nonexportable AES-GCM wrapping key, unique per-encryption nonce/tag and authenticated
PC/pin/credential-generation metadata. Key creation and Cipher operations need
separate approval. Key user-auth/device-unlock requirements, StrongBox support and
device lock behavior are owner choices, not portable guarantees. Never fall back to
plaintext/software export on unsupported hardware or KeyPermanentlyInvalidatedException.
Encrypted credential files must be excluded from backup/device transfer or require
explicit re-pair after restore; original allowBackup=false is not universal proof
across OEM transfer paths. Reinstall, profile removal, key invalidation or decryption
failure => lose local credential and re-pair, not restore trust silently. Keystore
confidentiality does not establish stored-state recency.

6. DURABLE CREDENTIAL / REVOCATION THREAT MODEL

Model per phone: opaque phone ID, snapshot.read scope, credential verifier only,
trust/identity generation, credential generation, issued/expiry evidence, durable
transaction version and revoked tombstone. No real token examples/issuance here.
Creation commits verifier+generation durably before token delivery. Rotation is
one atomic replacement invalidating prior generation; no implicit grace overlap.
Revocation installs local denial/fence BEFORE persistence, then atomically commits
tombstone and generation. Every commit is compare-version plus complete flush;
lost ack, partial write, corruption, unexpected version or rollback => UNCERTAIN,
deny all, stop listener if one exists. Never infer NOT-COMMITTED from an exception.
Repeated confirmed revoke is idempotent; uncertain revoke is not retried/repaired.
Crash after commit but before delivery may leave an orphan enrollment; expose only
local redacted uncertainty, require owner review/re-pair; no token replay/reissue.

Disk threat: attacker or backup restores an older well-formed DPAPI/Keystore-
protected image containing a now-revoked credential. Ciphertext integrity, ACLs,
write-through/flush and atomic rename prevent some corruption but not rollback.
An HMAC/digest/version kept in the SAME rollback domain is not an independent
freshness witness. Multiple local files/journal copies do not solve that alone.
OS crash and power-loss durability also need separate storage/volume evidence.
RESTART_LOCKED remains mandatory until an authenticated nonrollback authority and
reconciliation algorithm are proven and approved. No import/unlock shortcut exists.

Safer alternatives for owner decision:
A. Session-only authorization: every PC restart discards registry, requires fresh
local consent and explicit re-pair, never restores old verifiers. Fresh session
authority must be unpredictable and never reused; production policy/identity
lifetime still requires separate proof. Simpler, with usability cost.
B. Independent rollback-resistant authority (reviewed TPM-backed monotonic mechanism
or authenticated external witness). Adds platform/state/provisioning or external
availability/trust dependencies; none is approved, installed or assumed present.
C. A surviving phone as witness can detect SOME PC rollback only if that phone's
own state is trustworthy/current. Simultaneous rollback/loss/new phone has no proof;
not a general solution, no automatic unlock.
D. Keep all restored state locked and require owner reset/re-pair after review.
This is the current safe behavior, not a functioning durable credential system.
If product requirements demand unattended restored credentials with no trustworthy
witness, durable revocation may require a different architecture. Say NO-GO.

Response-commit authorization (proposed linearization contract):
1) Authenticate against generation g, parse/prepare bounded cached snapshot only;
   no HID/provider refresh. Preparation is not permission to send.
2) Under a per-credential/trust-generation coordinator, recheck active generation,
   expiry/clock and listener consent, then acquire a tracked response lease for g.
3) Enqueue/write only while lease remains valid; check at each write boundary.
   A naked check-then-await-write without coordination is a revocation race.
4) Revoke advances denial fence immediately, prevents new leases/queues, cancels
   old-generation writers, and waits for owned completion/abort acknowledgments.
   Do not report revocation complete while old leases can still enqueue bytes.
5) Persist tombstone/version with independently proven freshness; failure locks
   all responses and listener. Release/join in finally; uncertain exit => STOP.
Proposed guarantee: no NEW authorized enqueue after the revoke fence, and revoke
completion waits for old writers to end. Already sent/OS-buffered data cannot be
recalled and may arrive after revocation. Do not promise instantaneous remote
erasure or no post-click delivery. Native cancellation/queue semantics must be
proven before claiming even this contract. Existing fake lock tests do not prove it.

UTC determines certificate/credential windows; monotonic ticks only bound a single
boot/session. Never subtract across boot IDs or overflow counters. Backward/uncertain
time, untrusted boot identity or inconsistent elapsed evidence locks access. A
persisted last-seen UTC high-water mark is itself rollbackable; it is not trusted
time. Wall-clock forward jumps may expire early; do not silently extend/revive.
Choose a restart time authority/session-only alternative before durable unlock.
