## Controls and persistence

Automatic monitoring defaults **off**, interval **120 seconds**. Explicitly select 60, 120 or 300 seconds and select “Automatic HyperX monitoring (save preference)” to persist that choice in the application's LocalApplicationData `hyperx-monitoring.json`. Missing, corrupt, oversized or invalid preferences default off/120. Saving failure is reported and leaves only the current session choice. No percentage, timestamp, raw device path or acknowledgement is persisted.

The separate “Experimental HyperX queries” checkbox requires a warning acknowledgement once per application session. A saved enabled preference does **not** grant consent, start a helper, or query after restart. The owner must acknowledge again after restart, then the existing no-HID normal/forced-exit preflight must succeed. This preserves the Stage 4.0F session boundary. Enabling automatic monitoring after that explicit acknowledgement authorizes scheduled requests; it does not show a repeated prompt every interval. No elevation, service/driver change, NGENUITY closure or audio setting change is used.

Once receiver metadata, acknowledgement and preflight are ready, the first scheduled request waits a full selected interval. The scheduler's five-second metadata/state wakeup can add up to approximately five seconds plus discovery time; it does not send five-second battery queries. Scheduling is relative to completion, never a backlog of elapsed timer ticks. Opening/hiding the panel and metadata-only Refresh never query. Manual checks rebase the next scheduled check. Overlapping manual, scheduled and metadata events are dropped, not queued. A resumed healthy schedule also waits a full interval.

## State, reconnect and errors

The popup shows Battery candidate (ambiguous), Last successful candidate, Last checked, Next check/retry, and Paused/Error status. Receiver presence is separate from headset connectivity, which remains Unknown. Last checked is the request orchestration start time; observation time is recorded only for a validated candidate. No seeded startup value or ConfirmedFresh state exists. Detailed copied diagnostics include manual/scheduled origin, process observation, exact static target, request/output completion flags, error codes, elapsed time, cleanup/exit, failure count and schedule. No instance path/serial is copied.

A hidden Windows window subscribes to HID interface notifications. Exact target collection removal immediately marks the cached value Stale, disables querying and cancels owned work. Arrival does not query. A five-second metadata fallback also detects absent/ambiguous/incompatible targets, including when notification registration fails. That fallback is bounded in frequency, not a guarantee of instantaneous removal detection. After an **idle** removal/reconnect, exact metadata rediscovery waits a full interval, preserving an outstanding later failure-backoff deadline. The old reading stays Stale until a new candidate succeeds.

A normally exited helper with a well-formed negative result (timeout, malformed/absent report, access/sharing failure, unavailable receiver) may be retried only by a later scheduled check. Consecutive failures schedule 2, 5, then 15 minutes; the fourth failure suspends automatic mode. Interval edits/reconnect cannot shorten these deadlines. Success resets the failure count. Resume clears a recoverable suspension and waits a full interval; a user manual query remains explicit. Disabling automatic monitoring cancels active work and cancels scheduling. Cancellation pauses rather than silently restarting. It can require Resume after re-enabling.

**Crash, invalid IPC, forced exit, unknown process exit, failed containment or retained startup never clears the transport safety latch.** Resume cannot override it; inspect diagnostics and restart only after owner review. Unplug during an active native query can follow this stricter cancellation path, so automatic reconnect recovery is deliberately not promised after uncertain transport completion. No replacement helper is spawned while a prior operation remains unconfirmed. Cancel and application Exit await the supervisor's bounded cleanup; late replies cannot promote a reading or update destroyed controls. A driver may delay OS process termination indefinitely; unconfirmed exit is retained, not reported as cleanup success. The tray never owns active HID buffers.

NGENUITY may be observed running **or not observed** in the production provider/helper; unknown process inspection fails closed. Its state does not prove another client is absent, and the IPC nonce is not a HID transaction ID. The standalone POC's normal NGENUITY-closed and active-coexistence acknowledgement guards remain intact.

## Protocol and evidence limits

Exactly one target: `03F0:05B7 / MI_03 / COL01 / FF13:0001`, input/output/feature lengths `62/62/0`. One output `66 89` plus sixty zeros, one bounded input, three-second native exchange. The existing shared GENERIC_READ / FILE_SHARE_READ|WRITE / OVERLAPPED mode is reused. Validate 62-byte length, `66 89` header and byte-4 percentage 0..100; bytes 2/3 remain uninterpreted. No alternate command, feature API, automatic immediate retry, report dump or input stream is added.

Owner-supplied evidence: verified on-wire request/response; one concurrent POC candidate of 56% matched NGENUITY with nominal audio/application state. Subsequent experimental tray observations of 54%, and 52% after unplug/replug, also reportedly matched NGENUITY; receiver stale/rediscovery transitions worked and subsequent process listings showed no lingering named helper. These are **user-reported observations**, not cloud verification, unique response correlation, statistically reliable polling, or proof that every helper exited at every instant. A sleeping/off headset can time out or expose cached responses; a valid response does not prove headset connectivity or freshness. Automatic monitoring is implemented for review, with Windows sustained-use validation outstanding.

1. Build/run `test.ps1` with its existing execution-policy workaround and clipboard option. Run Windows UI and no-HID Job/process tests. Keep the full Debug publish folder, including `hyperx-helper`, together.
2. On upgrade/start, verify automatic off/120 for new preferences; a persisted enabled preference still waits for session acknowledgement and successful no-HID preflight. Opening/Refresh sends no battery request. Check interval edits, disabling, and save failure behavior.
3. **Only after reviewing/authorizing physical monitoring**, select automatic 120 seconds and acknowledge. Verify no immediate request and first check at approximately 120 seconds after readiness (up to one five-second wakeup/discovery delay). Record observation times and copied diagnostics; do not infer ownership from percentage agreement.
4. Supervise 10–15 minutes with NGENUITY/audio active, then separately with NGENUITY closed. Check one helper at a time, exit/cleanup on each attempt, interval spacing, no polling bursts and no accumulation. Stop on audio/app disruption; do not automatically repeat a failed experiment.
5. Verify idle receiver removal immediately disables querying and marks old data Stale; reconnect waits a full interval, preserving longer backoff. Separately review unplug-mid-query cancellation; a transport latch requires diagnostics/review, not forced Resume.
6. With fakes/no hardware, check 2/5/15-minute backoff, four-failure suspension and explicit Resume. On approved hardware, sleeping/off headset must never be inferred connected merely from receiver presence or cached percentage.
7. Exercise manual/automatic collision, Cancel, disable/re-enable, popup hiding, and Exit during a check. Verify one flight, no late UI updates, no orphan named helper, intact G915 reader/icon and G305 placeholder. Do not call unconfirmed termination cleanup success.
